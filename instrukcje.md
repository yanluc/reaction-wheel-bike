# Setup Guide: STM32 (NUCLEO-L4A6ZG) → Gazebo Harmonic over serial (Ubuntu 24.04 Noble)

The STM32 sends velocity commands over UART, and the robot `vehicle_blue` in Gazebo drives with them. Odometry flows back to the STM32. No ROS is involved: a small Python bridge talks to Gazebo directly via gz-transport.

```
STM32 LPUART1 ──ST-LINK VCP /dev/ttyACM0 @ 2 Mbaud──> gazebo/stm32_gz.py ──gz-transport──> gz sim
```

Details (protocol, firmware, troubleshooting): `gazebo/README.md`.

### Prerequisites & Compatibility Notes

* **OS:** Ubuntu 24.04 LTS (Noble Numbat)
* **Simulator:** **Gazebo Harmonic**
* **Board:** NUCLEO-L4A6ZG (MCU `STM32L4A6ZGTx`, *not* the `…TxP` SMPS variant), on-board ST-LINK/V2-1
* **STM32 tools:** STM32CubeMX (code generation), STM32CubeIDE 2.x (toolchain, programmer, debugger)

---

### Step 1: Install Gazebo Harmonic

Pick **one** option.

**Option A: already installed with ROS 2 Jazzy (the current setup on this machine).** Gazebo and its Python bindings live under `/opt/ros/jazzy/opt/*_vendor`, and `run.sh` sources `/opt/ros/jazzy/setup.bash` only to get those paths. No ROS process is started.

```bash
sudo apt install ros-jazzy-ros-gz   # pulls Gazebo Harmonic + Python bindings
```

**Option B: standalone Gazebo, no ROS at all** (official OSRF repository; not tested on this machine):

```bash
sudo apt-get update && sudo apt-get install curl lsb-release gnupg -y
sudo curl https://packages.osrfoundation.org/gazebo.gpg --output /usr/share/keyrings/pkgs-osrf-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/pkgs-osrf-archive-keyring.gpg] http://packages.osrfoundation.org/gazebo/ubuntu-stable $(lsb_release -cs) main" \
  | sudo tee /etc/apt/sources.list.d/gazebo-stable.list > /dev/null
sudo apt-get update
sudo apt-get install gz-harmonic python3-gz-transport13 python3-gz-msgs10 -y
```

---

### Step 2: Install Python Dependencies (system Python)

The bridge runs under `/usr/bin/python3`, not a venv, because the Gazebo bindings are built for the system interpreter.

```bash
sudo apt install python3-serial python3-protobuf -y
```

Check:

```bash
/usr/bin/python3 -c "from gz.transport13 import Node; import serial; print('ok')"
# Option A: run `source /opt/ros/jazzy/setup.bash` first
```

---

### Step 3: Grant Serial Port Permissions

```bash
sudo usermod -aG dialout $USER
```

*(Log out and log back in for the group change to take effect.)*

---

### Step 4: Firmware (`test_stm_gazebo/`)

All configuration lives in `test_stm_gazebo.ioc` and the code is generated by CubeMX. Hand-written code goes only between `USER CODE BEGIN/END` markers in `Core/Src/main.c`.

Current configuration:

* SYSCLK 80 MHz
* LPUART1 2 000 000 baud 8N1, overrun detection disabled
* RX via DMA2_Channel7 in circular mode

1. **Regenerate after changing the `.ioc`** (headless):
   ```bash
   cd test_stm_gazebo
   printf 'config load %s\nproject generate\nexit\n' "$PWD/test_stm_gazebo.ioc" > /tmp/gen.txt
   ~/STM32CubeMX/STM32CubeMX -q /tmp/gen.txt
   ```
2. **Build and flash.** Choose one:
   * **STM32CubeIDE:** **File → Import → STM32 CMake Project**, MCU `STM32L4A6ZGTx`, then build. Debug with **Run → Debug Configurations → STM32 C/C++ Application** (ST-LINK, SWD). If the wizard says *"Project location directory already contains an existing project"*, remove the stale `.project` first.
   * **CLI:**
     ```bash
     export PATH=/opt/st/stm32cubeide_2.2.0/plugins/com.st.stm32cube.ide.mcu.externaltools.gnu-tools-for-stm32.14.3.rel1.linux64_1.0.100.202602081740/tools/bin:$PATH
     cmake --preset Release && cmake --build --preset Release
     /opt/st/stm32cubeide_2.2.0/plugins/com.st.stm32cube.ide.mcu.externaltools.cubeprogrammer.linux64_2.2.500.202603051304/tools/bin/STM32_Programmer_CLI \
       -c port=SWD -w build/Release/test_stm_gazebo.elf -v -rst
     ```

---

### Step 5: Run

```bash
cd gazebo
./run.sh /dev/ttyACM0 2000000
```

This starts `gz sim` (GUI) with `diff_drive_stm32.sdf` and the bridge `stm32_gz.py`. After about 5 s the log should show `rx 50.0 frames/s, lost 0, crc errors 0`.

The world file is a copy of the gz-sim `diff_drive.sdf` example. The only change: `vehicle_blue` odometry runs at 50 Hz instead of 1 Hz.

**Controls on the board:**

| Element | What it does |
|---|---|
| **B1 (blue, USER)** | Cycles the mode: STOP → FORWARD → CIRCLE → RETURN_HOME → STOP |
| **B2 (black)** | RESET; the board restarts in STOP |
| **LD3 (red)** | Off when odometry from Gazebo reaches the STM32 (link OK) |
| **LD2 (blue)** | On while the robot is moving |

Only `vehicle_blue` is controlled; `vehicle_green` stays still.

### Troubleshooting

* **Robot doesn't move:** the default mode is STOP, so press B1. Also check that the simulation isn't paused (▶ button in Gazebo).
* **Port busy:** close any CubeIDE debug session or other serial terminal holding `/dev/ttyACM0`.
* **`crc errors` / `lost` keep growing:**
  1. Lower `LPUART1.BaudRate` in the `.ioc` (e.g. 1000000).
  2. Regenerate, rebuild and flash.
  3. Run `./run.sh /dev/ttyACM0 1000000`.

  2 Mbaud is the ceiling of the ST-LINK/V2-1 VCP (`lsusb` shows `0483:374b`). It has been verified on this board.
* **Two simulations running at once** (e.g. a test and the GUI) share gz-transport topics. Isolate them with `export GZ_PARTITION=<name>` per terminal.
